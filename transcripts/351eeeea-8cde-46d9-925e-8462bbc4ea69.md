## 3. Fraîcheur

Deux colonnes de plus sur `forecasts`, et un bloc commun à toutes les réponses.

```
forecasts
  + optimized_at  timestamptz NULL   -- posé au commit des recommended_prices
  + bookings_as_of int NOT NULL      -- ventes + annulations lues par le run
```

```
freshness: {
  forecast_computed_at:     datetime | null,
  optimization_computed_at: datetime | null,

```

- **Deux runs distincts** : le dernier forecast est `ORDER BY id DESC LIMIT 1`, la dernière optimisation est le dernier `forecasts` avec `optimized_at NOT NULL`. Ils peuvent différer, par exemple quand le worker est mort entre les deux commits ou quand l'optimisation est en cours. Les prix recommandés du grid viennent du run optimisé, pas du dernier forecast.
- **Compteur plutôt qu'horodatage** : `sale_datetime` est l'heure locale du système de réservation et un booking ancien peut arriver en retard. Un compteur ventes + annulations est robuste à ça, un timestamp ne l'est pas. `bookings_now - bookings_as_of` dit combien d'événements le run n'a pas vus.
- **Pending** : `EXISTS pending_forecasts` OU verrou advisory tenu sur le service. Sans la deuxième condition, un job en cours apparaît comme "rien en attente" entre le claim et l'écriture. La requête `pg_locks` existe déjà dans le worker.
