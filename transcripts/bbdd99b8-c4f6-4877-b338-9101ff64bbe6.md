# Domain Modeling

Actively build and sharpen the project's domain model as you design. This is the *active* discipline: challenging terms, inventing edge-case scenarios, and writing the glossary and decisions down the moment they crystallise. (Merely *reading* `GLOSSARY.md` for vocabulary is not this skill: that's a one-line habit any skill can do. This skill is for when you're changing the model, not just consuming it.)

## File structure

Most repos have a single context:

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
```

## During the session

### Challenge against the glossary

When domain relationships are being discussed, stress-test them with specific scenarios. Invent scenarios that probe edge cases and force the user to be precise about the boundaries between concepts.

### Cross-reference with code

When the user states how something works, check whether the code agrees. If you find a contradiction, surface it: "Your code cancels entire Orders, but you just said partial cancellation is possible. Which is right?"

Only offer to create an ADR when all three are true:

1. **Hard to reverse**: the cost of changing your mind later is meaningful
2. **Surprising without context**: a future reader will wonder "why did they do it this way?"
3. **The result of a real trade-off**: there were genuine alternatives and you picked one for specific reasons

If any of the three is missing, skip the ADR. Use the format in [ADR-FORMAT.md](./ADR-FORMAT.md).

## Ce que coûterait une file faite main

Ce n'est pas cher, parce que les décisions déjà prises simplifient beaucoup : un seul job par Service, pas de retry, et un échec est réparé par la prochaine Booking. Voici l'esquisse :

- **Table** `pending_services (service_id PK, queued_at)` : une ligne par Service qui attend un Forecast. Une seule migration de quelques lignes, à la place des 600 lignes de SQL de procrastinate.
- **Mise en file** dans la transaction de la Booking :
  ```sql
  INSERT ... ON CONFLICT (service_id) DO NOTHING;
  NOTIFY ...;
  ```
  Si le Service attend déjà, l'insert ne fait rien, sans erreur. Il n'y a donc plus de savepoint, plus de connexion psycopg à extraire de la session, et ça passe par la session SQLAlchemy normale. Le `NOTIFY` n'est envoyé qu'au commit.
- **Worker**, environ 50 lignes :
  - une boucle qui prend un Service en attente :
    ```sql
    DELETE ... WHERE service_id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING service_id
    ```
  - le `DELETE` est commité tout de suite. Une Booking qui arrive pendant le calcul remet donc le Service en attente, ce qui donne exactement le comportement 2b. Elle ne bloque pas non plus sur un verrou ;
  - un `pg_advisory_lock(service_id)` garantit qu'un seul calcul tourne par Service, même avec plusieurs workers ;
  - l'attente se fait par `LISTEN`, avec un réveil périodique au cas où une notification serait manquée, et l'arrêt reste propre sur SIGTERM.
- **Tests** : plus simples, sans remplacement de connecteur ni schéma vendorisé.

Au total, environ 80 à 100 lignes de code, contre une dépendance, un snapshot SQL et l'astuce du savepoint en moins. Ce qu'on perd :
- le statut et l'historique des jobs (`succeeded` / `failed`, les événements) ;
- les retries, les outils d'administration et la purge des workers bloqués.

**Les verrous classiques de Postgres** (`SELECT … FOR UPDATE` sur une ligne, `LOCK TABLE` sur une table) :
- ils portent sur une donnée réelle et bloquent toute opération concurrente sur cette donnée : écritures, autres `FOR UPDATE` ;
- ils sont toujours libérés à la fin de la transaction, on ne peut pas les garder au-delà.

**Un `pg_advisory_lock`** :
- il porte sur un simple nombre choisi par nous, ici le `service_id`. Postgres ne l'associe à aucune donnée et ne bloque rien d'autre que le code qui demande le même verrou ;
- en version session, il tient jusqu'à l'appel de `pg_advisory_unlock` ou la fermeture de la connexion, même à travers plusieurs commits ;
- si le worker plante, la connexion tombe et le verrou est libéré automatiquement.

**Pourquoi l'advisory ici.** Le besoin est « un seul calcul par Service », pendant 6 s et sur plusieurs commits : le Forecast est commité, puis les prix. Avec un verrou classique :
- **sur la ligne du Service** : il faudrait garder une transaction ouverte 6 s, et l'import du Transport plan serait bloqué pendant ce temps ;
- **sur la ligne en attente** : elle est supprimée au moment de la prise en charge et une Booking peut la recréer. La verrouiller ferait attendre la Booking 6 s, ce qu'on veut justement éviter.

L'advisory lock ne bloque aucune donnée, les Bookings n'attendent jamais, et il résiste à nos commits intermédiaires.

Le `lock` de procrastinate faisait la même chose côté application, avec une colonne dans sa table de jobs et un index unique sur le statut `doing`.

Deux précautions dans le code :
- l'espace des clés advisory est commun à toute la base. J'utilise donc la forme à deux entiers, `pg_advisory_lock(<constante "forecast">, service_id)`, pour ne pas entrer en collision avec un autre usage futur ;
